7. Patrones de Diseño y su Impacto en la Mantenibilidad

Circuit Breaker Pattern (BFF)

Implementado con la librería Opossum en CircuitBreakerService. Cada llamada HTTP a un microservicio está envuelta en un breaker con umbral del 50% de errores y timeout de 3 segundos. Si el microservicio cae, el circuito se abre y se desvía al fallback, evitando cascadas de fallos. Beneficio de testing: al aislar la lógica del breaker en un servicio inyectable, se puede probar independientemente de las llamadas HTTP reales.

Repository Pattern (NestJS + TypeORM)

TypeORM implementa el patrón Repository a través de Repository<Entity>. Los servicios NestJS reciben el repositorio por inyección de dependencias (@InjectRepository), lo que permite que en los tests unitarios se sustituya por un mock sin modificar el servicio bajo prueba. Beneficio de testing: los tests pueden simular findOne, save, delete sin una base de datos real.

DTO (Data Transfer Object) Pattern

Todos los microservicios definen DTOs separados para crear y actualizar recursos (ej.: CreateOrderDto, UpdateOrderStatusDto). Al decorar con class-validator, la validación ocurre antes de llegar al servicio, centralizando la lógica de validación. Beneficio de testing: los DTOs son plain classes con 100% de cobertura sin necesidad de infraestructura.

BFF (Backend for Frontend) Pattern

El BFF centraliza la orquestación de llamadas HTTP hacia los cuatro microservicios, maneja la autenticación JWT y aplica el circuit breaker. El frontend solo conoce un único endpoint de entrada. Beneficio de testing: cada microservicio puede testearse de forma aislada; el BFF prueba la lógica de orquestación mockeando HttpService.

MVC en Express (ms-shipping)

El microservicio de despacho aplica MVC explícitamente: envios.model.js (Model/Mongoose), envios.controller.js (Controller) y envios.router.js (routing/View-layer en REST). La separación facilita el mock total del Model en los tests del Controller, logrando 100% de cobertura sin conectarse a MongoDB.

8. Ejemplo Representativo de Prueba

Test del controlador de shipping – caso de creación con datos duplicados:

it('devuelve 400 ante duplicado (código 11000)', async () => {
  // Arrange
  const dupErr = new Error('dup');
  dupErr.code = 11000;
  Envios.mockImplementation(() => ({ save: jest.fn().mockRejectedValue(dupErr) }));

  const req = { body: { order: validOrder, formManualData: validForm } };
  const res = mockRes();

  // Act
  await EnviosController.create(req, res);

  // Assert
  expect(res.status).toHaveBeenCalledWith(400);
  expect(res.json).toHaveBeenCalledWith(
    expect.objectContaining({ error: expect.stringContaining('Ya existe un despacho') })
  );
});

Este test valida que el manejo del error de clave duplicada de MongoDB (código 11000) se traduce en una respuesta HTTP 400 con un mensaje de negocio claro, sin exponer detalles internos al cliente.
