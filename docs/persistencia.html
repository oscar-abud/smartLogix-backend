Descripción de la Persistencia – SmartLogix

Evaluación Parcial 3 · Fullstack III · Duoc UC

1. Visión General de la Arquitectura de Datos

SmartLogix implementa una estrategia de persistencia políglota: tres microservicios usan PostgreSQL mediante TypeORM (datos estructurados y relacionales), mientras que el microservicio de despacho usa MongoDB Atlas mediante Mongoose (documentos semiestructurados y flexibles).

2. ms-users – TypeORM + PostgreSQL

Entidades y relaciones

TablaColumnas claveRelación
users id (UUID PK), email (unique), password, role_id (FK), createdAt ManyToOne → Role
roles id (PK), name OneToMany → User

Implementación técnica

TypeORM es inicializado en AppModule mediante TypeOrmModule.forRoot() con la opción synchronize: false en producción. Las entidades se registran con el decorador @Entity y TypeORM genera automáticamente las consultas SQL. La relación @ManyToOne con eager: true garantiza que el rol sea cargado junto al usuario en cada consulta sin necesidad de un JOIN manual.

La clave primaria de users usa uuid generado automáticamente, lo que evita colisiones entre instancias y facilita la portabilidad del identificador hacia otros microservicios.

3. ms-inventory – TypeORM + PostgreSQL

Entidades y relaciones

TablaColumnas claveRelaciones
inventories id (PK), name, description, created_at OneToMany → InventoryItem, OneToMany → UserInventory
inventory_items id (PK), sku, name, price, stock_available, stock_reserved, inventory_type_id (FK), inventory_id (FK) ManyToOne → Inventory, ManyToOne → InventoryType
inventory_types id (PK), name OneToMany → InventoryItem
user_inventory inventory_id (FK), user_id ManyToOne → Inventory (tabla de unión)

Implementación técnica

Este microservicio expone la lógica de stock mediante el método updateStock del servicio, que realiza operaciones atómicas sobre stock_available y stock_reserved usando el repositorio TypeORM (Repository<InventoryItem>). La separación entre stock disponible y reservado permite reflejar las órdenes en tránsito sin comprometer la disponibilidad real.

La tabla user_inventory actúa como tabla de unión para la asignación de operadores a almacenes, sin necesidad de duplicar datos de usuario en este microservicio (el user_id viene del JWT del BFF).

4. ms-orders – TypeORM + PostgreSQL

Entidades y relaciones

TablaColumnas claveRelaciones
orders id (PK autoincrement), status (enum), total_amount (decimal 12,2), createdAt OneToMany → OrderItem (cascade)
order_items id (PK), order_id (FK), product_id, quantity, price (decimal 10,2) ManyToOne → Order (onDelete CASCADE)

Implementación técnica

La relación OneToMany con cascade: true en Order.items permite guardar la cabecera y todos los ítems en una sola operación repository.save(order). El campo status está tipado como un enum de TypeScript (PENDING | PROCESSED | CANCELLED), lo que impone restricciones a nivel de modelo antes de llegar a la base de datos.

El product_id en order_items es una referencia lógica hacia ms-inventory, sin clave foránea física entre bases de datos, respetando la independencia de cada microservicio.

Implementación técnica

El esquema se define mediante mongoose.Schema con la opción timestamps: true, que genera automáticamente createdAt y updatedAt en cada documento. La restricción unique: true sobre orderId garantiza que no se pueda registrar dos veces el despacho de la misma orden (error MongoDB code 11000).

El campo shippingStatus usa validación de enum nativa de Mongoose, evitando estados inválidos sin necesidad de validación adicional en el controlador. La conexión a MongoDB Atlas se realiza mediante el URI mongodb+srv con retryWrites: true para tolerancia a fallos de red.

A diferencia de las tablas relacionales, el documento Envío combina datos provenientes de dos fuentes (la orden en PostgreSQL y el formulario del operador) en un único documento JSON desnormalizado, optimizando la lectura del historial logístico.

Razón de MongoDB en ms-shipping: Los registros de despacho tienen estructura variable (distintos campos opcionales por destino) y se acceden principalmente por lectura histórica, lo que favorece el modelo documental sobre el relacional.

6. Comunicación entre Motores

No existe ninguna conexión directa entre los motores de base de datos. La integración de datos entre microservicios ocurre exclusivamente a través de HTTP REST: el BFF orquesta las llamadas entre ms-orders (PostgreSQL) y ms-shipping (MongoDB), pasando el objeto JSON de la orden en el body del POST. Esto mantiene la independencia de despliegue y la tolerancia a fallos entre bases de datos.
